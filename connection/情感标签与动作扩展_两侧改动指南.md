# 情感标签与动作扩展：两侧改动指南

> 本文回答一个问题：**后续要新增情感标签、新增机器人动作时，对话侧和机器人侧分别要改什么。**
>
> 与《情感标签驱动机器人动作_LLM_Robot连接程序任务书.md》的关系：任务书负责"生成连接程序"这一次的实现；本文负责连接程序上线之后的**扩展维护**。桥接层（连接程序本身）的扩展永远只是改 `bridge_config.json`，真正的改动量在两侧。

---

# 0. 全景：三种扩展场景 × 三个改动位置

| 场景 | 对话侧<br>companion-agent-memory | 机器人侧<br>/home/nvidia/sim2real | 桥接层<br>bridge_config.json |
|---|---|---|---|
| **A. 新增情感标签**（如 `生气`） | **必改**：`emotion_detector.py` + 测试 + 前端样式 + 文档 | 不改 | 可选：加映射才会触发，不加则静默跳过 |
| **B. 新增机器人动作**（如 `comfort_low`） | 不改 | **必改**：部署三件套 + 注册 + 重启 + 验证 | **必改**：whitelist + duration |
| **C. 已有标签绑定已有动作** | 不改 | 不改 | **必改**：`emotion_map` 加一行 |

一条铁律贯穿全文：**桥接层的 `emotion_map` 里写的是动作名（如 `wave_v73_rt`），不是动作文件路径。** 动作名 → motion YAML → TRT + future JSON 的解析由机器人侧的 Sim2Real 注册表完成；把路径写进映射等于绕过注册系统，属于错误层级，禁止。

---

# 1. 场景 A：新增情感标签（对话侧改动）

## 1.1 为什么必须改对话侧代码

`companion_agent/emotion_detector.py` 对标签做了**三重硬限制**，LLM 判出的标签只要不在白名单里就会被当作非法值回退到本地规则判断（`_detection_from_judge()` 的校验，约 L230）。所以新增标签不是"LLM 自然能输出"的事，必须显式放行：

1. `ALLOWED_LABELS` 常量集合（合法标签白名单）；
2. `_system_prompt()` 里写给 LLM 的合法标签列表；
3. 本地规则词表（LLM 调用失败时的兜底判断）。

## 1.2 改动清单（精确到位置）

以下行号为当前代码的近似位置，以名称定位为准。

### 必改

| # | 文件 | 位置 | 改什么 | 不改的后果 |
|---|---|---|---|---|
| 1 | `companion_agent/emotion_detector.py` | 常量区，约 L12 | 新增标签常量，如 `EMOTION_ANGRY = "生气"` | — |
| 2 | 同上 | `ALLOWED_LABELS`，约 L31 | 加入新常量 | LLM 判出该标签也会被当非法值，回退规则判断 |
| 3 | 同上 | `POSITIVE_LABELS` / `NEGATIVE_LABELS`，约 L32–33 | 按极性加入（生气 → NEGATIVE） | `trend` 推断（持续/加重/缓解中）退化，跨标签转移一律算"波动" |
| 4 | 同上 | `_system_prompt()`，约 L198–207 | "Allowed label values are exactly: None, 开心, 难过" 这一行加入新标签 | LLM 根本不会输出新标签 |
| 5 | 同上 | 词表 `HAPPY_TERMS` / `SAD_TERMS`，约 L36–58 | 为新标签补兜底触发词（如生气加 `生气/愤怒/气死/火大/恼火`） | LLM 失败时规则兜底认不出新标签，静默变 `None` |
| 6 | `tests/test_emotion_detector.py` | — | 为新标签加正/反例用例 | 回归无保障 |

### 需要评估的（新极性组才有）

| # | 文件 | 位置 | 说明 |
|---|---|---|---|
| 7 | `companion_agent/emotion_detector.py` | `detect_by_rule()`，约 L84–114 | **注意**：当前规则打分是开心/难过**二分类硬编码**（`label = EMOTION_SAD if sad_score >= happy_score else EMOTION_HAPPY`）。如果新标签仍归入"正面/负面"两类，只需把新词并入对应词表即可；如果要引入独立第三类（如"中性惊讶"），这段要重写成多组取最大分的逻辑——这是对话侧唯一的实质性代码改动，其余都是加常量/加词 |

### 建议同步的（不影响功能，影响一致性）

| # | 文件 | 位置 | 说明 |
|---|---|---|---|
| 8 | `prototype_demo/static/styles.css` | `data-emotion` 样式，约 L477–493 | 现有 `开心`/`难过` 各有徽章配色；新标签不加样式会回退默认灰色，仅显示问题 |
| 9 | `MEMORY.md`（companion-agent-memory 项目内） | 约第 12 节情绪部分 | 现文档写"限制在 None、开心、难过 三个标签"，同步更新 |

### 确认不用改的（容易误判）

| 文件 | 原因 |
|---|---|
| `prototype_demo/server.py` 的 `persist_emotion_output()` | `label` 纯透传，默认值 `"None"`，对任意标签成立 |
| `prototype_demo/static/app.js` | 情绪徽章渲染是通用逻辑（`emotion?.label \|\| "None"`），任意标签直接显示 |
| `current_emotion.json` 格式 | 字段结构不变，只是 `label` 多了一个取值 |

## 1.3 验证方法

1. 跑单测：`pytest tests/test_emotion_detector.py`；
2. 起对话服务，说一句含新标签情绪的话（如"我真的气死了"）；
3. 检查 `prototype_demo/.run/current_emotion.json` 的 `emotion.label` 是否为新标签；
4. 看前端情绪徽章是否正常显示（颜色 + 文案）。

## 1.4 对桥接层的影响

零改动也安全：`emotion_map` 里没有的标签，watcher 一律"不触发 + 记 info 日志"。所以**对话侧可以先独立上新标签**，之后再决定给不给它绑动作。

# 2. 场景 B：新增机器人动作（机器人侧改动）

## 2.1 前置产物：从训练服务器带回"三件套"

一个动作在真机上跑起来需要三个文件（以 `wave_v73_rt` 为参照，产出流程详见《Mini_Pi_Plus_自采动作到真机部署完整指南.md》）：

```text
config/motion/<动作名>.yaml         ← 单动作总配置（绑定下面两个文件 + 算法 + motor group）
policy/motion/<动作名>_action.trt   ← TensorRT 策略（训练服务器 .pt → .onnx → Orin 上 trtexec 转换）
config/future/motion/<动作名>.json  ← 未来参考轨迹（训练 .npz → sim2sim.py --save_json）
```

## 2.2 部署到真机路径

```text
/home/nvidia/sim2real/install/share/sim2real/config/motion/<动作名>.yaml
/home/nvidia/sim2real/install/share/sim2real/policy/motion/<动作名>_action.trt
/home/nvidia/sim2real/install/share/sim2real/config/future/motion/<动作名>.json
```

写 `<动作名>.yaml` 时参照 `wave_v73_rt.yaml` 的结构：`policy_name` / `future_file_name` / `algorithm` / `motor_group` / `dofs`，`motion_len` 按新动作 future JSON 实际长度设置，不要照抄旧值。

## 2.3 注册进动作注册表

```text
/home/nvidia/sim2real/install/share/sim2real/config/pi_plus_26dof_config/pi_plus_26dof_rl_config_custom.yaml
```

操作规范（来自部署指南第 19 节）：

1. **先备份**：`cp ...yaml ...yaml.bak_$(date +%Y%m%d_%H%M%S)`；
2. 复制一条已有 motion 条目（如 `wave_v73_rt`）；
3. **只改**动作名称和 YAML 路径；
4. 保持缩进与原有条目完全一致。

## 2.4 手柄按键入口（仅触发实现 B 需要）

如果桥接层用手柄模拟兜底（`trigger_impl: "B"`），还需在

```text
/home/nvidia/sim2real/install/share/sim2real/action_config/config/<当前机型目录>/
```

的 `base_policy.yaml` / `custom_action.yaml` 中为新动作注册按键组合；直连接口（实现 A）不需要。新增动作后记得重抓一次 `/joy` 按键序列，回填 `bridge_config.json` 的 `joy_button_sequence`（如果该动作用独立按键）。

## 2.5 重启与验证

1. 重启主控使注册生效：
   ```bash
   cd /home/nvidia/sim2real && source ./install/setup.bash
   roslaunch sim2real_master joy_control_pi_plus_orin.launch
   ```
2. 验证注册成功：默认模式正常进入；日志能看到新动作名；不提示找不到 motion / policy；不因错误入口进保护；
3. **先用手柄短周期试一次**，确认无异常后再交给桥接层触发；
4. 首测安全要求（部署指南第 21 节）：开阔防滑地面、周边无人、有人值守可扶、手柄急停可用、测试者不站机器人正前方、第一次只跑一个短周期。

## 2.6 机器人侧红线

- 不改 `dof_type = 26`（不为 22 DoF 的动作 policy 改启动参数）；
- 不动 `wave_v73_rt` 及其他已验证动作的任何文件；
- 不使用大范围 `kill` 清理进程。

## 2.7 对桥接层的影响（必改）

`bridge_config.json`：

```json
"actions": {
  "wave_v73_rt": { "duration": 6.5 },
  "comfort_low": { "duration": 8.0 },
  "whitelist": ["wave_v73_rt", "comfort_low"]
}
```

- `whitelist` 必须与机器人注册表保持一致——gateway 按它拒绝未注册动作；
- `duration` = 动作实际时长 + 余量（从 future JSON 的帧数 ÷ 50 FPS 得出，如 272 帧 ≈ 5.44 s → 配 6.5）；
- 改完配置**重启 watcher 和 gateway**（配置在进程启动时加载）。

# 3. 场景 C：已有标签绑定已有动作（纯桥接层）

前提：标签已存在于 `current_emotion.json` 的合法值中，动作已在机器人注册表且已在 whitelist。

`bridge_config.json` 三步：

```json
"emotion_map": {
  "开心": "wave_v73_rt",
  "难过": "wave_v73_rt",
  "生气": "comfort_low"
}
```

1. `emotion_map` 加一行 `"标签": "动作名"`；
2. 确认动作在 `actions.whitelist` 里（不在则按场景 B 补）；
3. 确认 `actions.<动作名>.duration` 已配置。

重启两个进程生效。验证：dry-run 模式下说一句触发该标签的话，看日志出现 `TRIGGER ... action=<动作名>`；再切实机。

# 4. 完整示例：新增「生气」标签 + comfort_low 安抚动作

一次跨越两侧的完整扩展，按推荐顺序执行：

## 第 1 步：对话侧放行「生气」

```python
# companion_agent/emotion_detector.py 常量区
EMOTION_NONE = "None"
EMOTION_HAPPY = "开心"
EMOTION_SAD = "难过"
EMOTION_ANGRY = "生气"          # 新增

# 类属性
ALLOWED_LABELS = {EMOTION_NONE, EMOTION_HAPPY, EMOTION_SAD, EMOTION_ANGRY}
POSITIVE_LABELS = {EMOTION_HAPPY}
NEGATIVE_LABELS = {EMOTION_SAD, EMOTION_ANGRY}   # 生气归负面，trend 推断才能算出"加重/缓解中"

# 词表（并入 SAD_TERMS 或单列均可，因为都是负面组）
SAD_TERMS = (..., "生气", "愤怒", "气死", "火大", "恼火")
```

`_system_prompt()` 中改为：

```text
Allowed label values are exactly: None, 开心, 难过, 生气.
```

（生气与难过同属负面，`detect_by_rule` 二分类逻辑不用动。）加测试用例、加 CSS、更新 MEMORY.md。

**此时桥接层不改**：生气标签出现时 watcher 记 `SKIP label=生气`，安全。

## 第 2 步：机器人侧部署 comfort_low

按第 2 节：三件套到位 → 注册进 `pi_plus_26dof_rl_config_custom.yaml`（先备份）→ 重启 launch → 手柄短周期验证 → 安排首测安全环境。

## 第 3 步：桥接层接线

```json
"emotion_map": { "开心": "wave_v73_rt", "难过": "wave_v73_rt", "生气": "comfort_low" },
"actions": {
  "wave_v73_rt": { "duration": 6.5 },
  "comfort_low": { "duration": 8.0 },
  "whitelist": ["wave_v73_rt", "comfort_low"]
}
```

重启 watcher + gateway。dry-run 验证日志 → 真机验证。

# 5. 推荐上线顺序（每步可独立验证、可回退）

```text
1. 对话侧先上新标签        → 桥接层未知标签静默跳过，零风险
2. 机器人侧部署并注册动作   → 用手柄验证，与桥接层无关
3. 桥接层加映射 + 白名单    → dry-run 看日志
4. 切 real 真机联调        → 有人在旁值守
```

反过来做（先配桥接层）的问题：映射指向未注册动作 → 触发必然失败；映射指向未放行的标签 → 标签永远不会出现，配置空转。

# 6. 常见错误对照表

| 错误 | 现象 | 正确做法 |
|---|---|---|
| `emotion_map` 里写了动作文件路径 | gateway 白名单校验失败，返回 400 | 写动作名，路径解析交给 Sim2Real 注册表 |
| whitelist 加了动作，机器人侧没注册/没重启 | 触发时 ROS 调用失败，error 日志 | 先完成场景 B 的 2.2–2.5，再加 whitelist |
| 只改了 `_system_prompt`，没改 `ALLOWED_LABELS` | LLM 输出被当非法值回退，标签时有时无 | 两处必须同时改 |
| 新负面标签没进 `NEGATIVE_LABELS` | `trend` 跨标签转移全变"波动" | 按极性加入集合 |
| 规则词表没补新词 | LLM 超时/失败时标签静默变 `None` | 词表同步补 |
| 改完 `bridge_config.json` 不重启进程 | 配置不生效（启动时加载） | 重启 watcher + gateway |
| 新动作照抄旧动作的 `motion_len` | 动作截断或拖尾 | 按新 future JSON 帧数设置 |
| 为动作 policy 把 `dof_type` 改成 22 | 启动配置与 26 DoF 硬件不符 | 保持 26 |

# 8. 一句话总结

> **桥接层扩展永远只改配置；真正的工程量在两侧**——新标签改对话侧 `emotion_detector.py`（常量 + 提示词 + 词表三处同步），新动作改机器人侧（三件套部署 + 注册表 + 重启验证）。顺序永远是：对话侧 → 机器人侧 → 桥接层 → dry-run → 真机。
