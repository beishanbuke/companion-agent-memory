# 16.7 记忆架构和隐私规则仍未定义

当前系统已经实现了基础的长期记忆能力，并在最近的工作中进一步加入了 Memory Router v2 和 Memory Lifecycle v1。Memory Router 主要负责判断当前对话是否需要调用记忆，以及应该检索哪些记忆层；Memory Lifecycle 则在记忆进入 prompt 前补充新鲜度、可信度、生命周期状态等信息，避免被纠正、删除或过期的记忆继续影响回答。

但是，从真实长期陪伴型 Agent 的角度看，当前文档和实现仍然主要集中在交互原则、记忆检索和记忆注入策略上，还没有完整定义记忆架构和隐私规则。也就是说，系统已经能够在单用户 demo 场景下展示“记住”和“使用记忆”的能力，但如果要进入多用户、长期使用或更接近真实部署的场景，还需要进一步明确以下边界。

## 1. 短期记忆、项目记忆和长期记忆的技术边界

当前系统主要使用五层长期记忆模型，包括用户档案、偏好、长期目标、事件记忆和安全笔记。但不同时间尺度的记忆边界还需要更清楚地定义。

短期记忆应主要指当前会话窗口内的信息，例如最近几轮对话、当前任务上下文、用户刚刚提到但不一定需要长期保存的内容。这类记忆适合保存在 conversation history 中，随着会话结束或窗口滑动自然失效。

项目记忆可以理解为围绕某个任务、角色卡或项目产生的中期上下文，例如某个学习计划、某段代码重构需求、某个角色设定下的交互偏好。这类记忆不一定应该进入全局长期记忆，而应该有明确的 project/session namespace。

长期记忆则是跨会话保留的稳定信息，例如用户身份信息、长期偏好、重要目标、反复出现的情绪模式和安全相关提醒。这类记忆需要经过更严格的写入策略、生命周期管理和隐私控制。

后续需要在技术文档中明确三类记忆的存储位置、检索入口、默认生命周期和注入优先级，避免短期信息被误写入长期记忆，也避免长期信息在不相关任务中过度注入。

## 2. 默认保存期限仍需定义

目前 Memory Lifecycle v1 已经引入了不同 Tier 的新鲜度衰减规则，例如事件记忆比用户档案衰减更快，安全笔记不自动衰减。但这仍然属于注入前的派生规则，并不等同于完整的数据保留策略。

后续需要定义默认保存期限，例如：

1. 短期会话记忆默认只保留在当前 session 或有限历史窗口中。
2. 项目记忆默认随项目结束、角色卡删除或用户手动清理而归档。
3. 长期偏好和用户档案可以长期保存，但需要允许用户查看、修改和删除。
4. 事件型记忆可以设置默认归档周期，例如 30 到 90 天后降权或进入历史状态。
5. 安全相关记忆不应简单自动删除，但调用和展示需要更严格限制。

保存期限不应该只由技术实现决定，也应该结合用户可控性和隐私风险进行设计。

## 3. 多用户身份认证和记忆隔离仍未完成

当前 demo 环境仍然更接近单用户、本地 JSON 存储的形态。如果进入多用户环境，需要首先解决身份认证和用户级隔离问题。

多用户场景中，每条记忆都应该绑定明确的 `user_id`、`session_id`、`project_id` 或 `character_card_id`。检索时必须先经过身份和作用域过滤，再进入语义检索和 Memory Router 判断。否则可能出现一个用户的长期记忆被另一个用户或另一个角色上下文错误调用的问题。

后续需要补充：

1. 用户身份认证机制。
2. 用户级 namespace。
3. 项目级或角色卡级 namespace。
4. 多用户环境下的记忆访问权限检查。
5. 防止跨用户、跨项目、跨角色误检索的测试用例。

在这些机制完成前，系统更适合定位为单用户原型或本地 demo，不应直接用于真实多用户部署。

## 4. 私密记忆在多人环境中的调用规则仍需明确

长期陪伴型 Agent 会不可避免地接触用户的私密信息，例如身份、位置、健康、关系、心理状态、家庭情况等。当前系统已经有 `safety_notes` 和隐私等级的初步设计，但还没有完整定义私密记忆在多人环境中的调用规则。

后续应把记忆按隐私级别区分，例如：

1. `public`：普通偏好或非敏感信息，可以在相关场景中使用。
2. `personal`：个人信息，只能在当前用户授权的上下文中使用。
3. `sensitive`：健康、心理、位置、关系、财务等敏感信息，默认不主动注入。
4. `restricted`：高风险或强隐私信息，需要用户明确确认后才能调用或展示。

对于多人环境，私密记忆的默认规则应该是最小可见：除非当前身份、场景和用户意图都明确匹配，否则不调用。即使被调用，也应避免在多人可见的对话环境中直接复述敏感内容。

## 5. 记忆删除、撤回和审计机制仍需补齐

当前系统支持删除记忆或清空记忆的 API，并且底层结构化记忆中存在 `deleted` 状态。但从隐私合规和用户信任角度看，还需要更完整的删除、撤回和审计机制。

需要区分三种操作：

1. 软删除：将记忆标记为 `deleted`，不再检索和注入，但保留内部记录用于冲突追踪或调试。
2. 物理删除：从持久化存储中彻底移除，满足用户“彻底忘记”的要求。
3. 撤回写入：用户发现系统误记后，可以撤回某条记忆，并要求系统不要继续基于它推理。

此外，还需要审计日志记录关键操作，例如某条记忆何时被写入、何时被更新、何时被检索、是否被注入 prompt、何时被用户删除或撤回。审计日志不应暴露给不具备权限的用户，但应该支持开发调试和用户权益请求。

## 6. 检索置信度与确认阈值仍需定义

Memory Router v2 已经加入了 `confidence`、`signals` 和 `tier_scores`，Memory Lifecycle v1 也为单条记忆计算了 `confidence` 和 `freshness`。但目前还缺少统一的确认阈值规则。

后续需要定义：

1. Router 置信度低于某个阈值时，不主动调用长期记忆。
2. 单条记忆的 lifecycle confidence 或 freshness 低于阈值时，只能作为弱背景，不能作为确定事实使用。
3. 当系统准备使用敏感记忆或低置信度记忆时，应先向用户确认。
4. 当多条记忆互相冲突时，应避免直接下结论，而是提示用户确认当前真实情况。

例如，当系统检索到“用户喜欢拿铁”和“用户后来不喝拿铁了”两条信息时，不应该继续直接推荐拿铁，而应该优先使用更新、更高置信度的记忆；如果冲突无法解决，则应该询问用户当前偏好。

## 7. 用户是否能查看机器人“记得什么”仍需产品化

当前系统已经有记忆看板和 `lifecycle_trace`，技术上具备展示记忆状态的基础。但用户是否能查看、编辑、删除机器人“记得什么”，还需要进一步产品化。

长期陪伴型 Agent 应该提供记忆透明机制，让用户知道系统记住了哪些信息，并能控制这些信息如何被使用。后续可以设计 Memory Inspector 或用户版记忆管理页，支持：

1. 查看当前长期记忆。
2. 查看记忆所属类型，例如 profile、preferences、goals、events、safety_notes。
3. 查看记忆状态，例如 active、stale、historical、contradicted、deleted。
4. 手动删除、修改或标记某条记忆。
5. 查看某条记忆是否会被用于回答。
6. 对敏感记忆设置“不主动使用”或“每次使用前询问”。

这部分不仅是调试工具，也会直接影响用户信任。对于长期陪伴型 Agent，用户需要知道系统不是在不可见地积累个人信息，而是在可控、可解释的边界内使用记忆。

## 小结

综上，目前系统已经具备了较清晰的记忆检索、分层和生命周期管理雏形，但记忆架构和隐私规则仍然需要进一步定义。下一阶段应该把工作重点从“记忆是否能被调用”扩展到“记忆属于谁、保存多久、在什么场景下能被调用、用户如何查看和删除、低置信度或敏感记忆如何确认”。这些规则会决定系统能否从单用户 demo 走向更可信的长期陪伴型 Agent。
